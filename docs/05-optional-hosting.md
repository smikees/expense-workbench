# Optional cloud hosting

Local is the default. Only proceed when the recipient asks for remote access. The preferred split keeps Firefly, bank credentials, raw imports and the bank worker on their computer; a PHP HTTPS host receives the dashboard code and reporting snapshots. A fully cloud-hosted bank worker is a separate architecture choice: use private networking, secret management, encrypted backups and an owner-approved threat model. Do not expose Firefly or the importer merely to host the dashboard.

The included `scripts/deploy.py` supports explicit FTPS and an Apache-compatible PHP 8.3+ host with SQLite3 and mbstring. Choose a dedicated empty subdomain document root. Set the provider's certificate-covered FTPS hostname, never disable certificate verification to accommodate an alias. A host offering only insecure FTP is unsuitable for financial snapshots. For SFTP/SSH or a managed container host, adapt transport using the same strict allowlist and tests; the included helper does not claim support for every host.

In ignored `private/settings.json`, set `site_origin` to the recipient's HTTPS origin and `hosting` to an object with `host`, `port`, `username`, `password`, and `directory`. Enter secrets using a local editor/secret prompt, not chat. `site/.private/config.json` contains password hashes and a random service token; add more users by securely hashing their chosen passwords, never copying plaintext into config. Both users share the household ledger and notes; this is not tenant isolation.

Initial deployment: `python scripts/deploy.py --initialize`. It requires an empty target, sets private denial first, uploads only app assets/site hashes/service token, and seeds the new notes database once. Subsequent deployment: `python scripts/deploy.py`. It preserves remote notes, backs up replaced app files and verifies upload bytes before rename. Never use `--initialize` to repair a missing live notes database: restore the authoritative website backup instead. No worker settings, bank keys, raw imports or Firefly database are in the upload allowlist.

Require DNS and valid HTTPS first. The app verifies the configured host and HTTPS at runtime; do not trust arbitrary forwarded headers. If hosting uses a trusted TLS proxy, configure the web server to convey HTTPS securely, or adapt the check to a strictly trusted proxy list. Apache must honor `.htaccess` private denial and rewrite rules. Nginx needs equivalent denial for `.private`, dotfiles and PHP source plus a front-controller allowlist; don't deploy unchanged under a server that ignores those rules.

After deployment, test HTTPS login/logout, bad-password throttling, session expiry, cross-origin note rejection, direct private-file denial and a note conflict. Confirm authenticated API data matches the expected snapshot and use a browser to inspect all views. Test both configured users. Then set hosting as the one authoritative notes location; the included local router forwards there. Scheduled note processing must fetch the website and stop on failure, without falling back to earlier local notes.

The transfer helper's FTPS verification is necessary but not sufficient: publication is complete only after the web smoke checks. If security tests fail, remove/block access at the web server and preserve the previous deployment/backups. Never claim deployment success because files were uploaded.
